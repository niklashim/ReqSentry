# Searchable incident request samples

ReqSentry saves **up to five request samples per incident**, then searches only that saved evidence. Ten incidents on a server produce at most fifty entries; a site filter returns only requests from that site. This does not create an archive of every access request.

The sampler keeps at most ten normalized samples per tracked identity, across the current and preceding analysis epochs. It selects the most recent available five within the same observed analysis window and client/site scope when the incident is scored. Global incidents can include multiple sites, but every sample retains its actual site and searches filter that field. Allowlisted requests are excluded from per-client evidence. Degraded aggregation suspends new rich samples. Fewer than five samples can therefore be available; samples are investigation examples, not a statistically representative population. Counters, detection signals, scores, and event IDs do not depend on sampling.

Samples contain logged timestamp, configured site, resolved client IP, method, bounded path, status, optional request/trace IDs, bytes and response time. Raw lines, query strings, referrers, user agents, forwarded headers and bodies are omitted. Strings are bounded and control characters are normalized; copied strings do not retain large parser buffers. Paths and identifiers can still contain application-specific sensitive values, so log producers should avoid those values. Timestamp/measurement absence remains explicit.

Samples are saved in the incident snapshot and indexed as child rows in the same SQLite transaction. Stable event-ID deduplication does not append another set of samples. Parent deletion removes the search rows, signals and traffic window together. The shared `database.retention.max_age` ceiling defaults to `96h`; local JSONL evidence follows the same ceiling. Previously saved incidents remain valid but have no fabricated/backfilled request samples.

The dashboard’s **Incident logs** page supports text and server/site/IP/method/status/date filters, bounded pagination, and links to the incident score. Site and incident pages provide site-scoped shortcuts. Incident-list text filtering returns incidents whose saved request samples match. Text search is a case-insensitive literal substring, including literal `%`/`_` characters; it is not regex or a general query language. Dates select the parent incident’s detection time, while rows display each request’s logged time. Repeated/overlapping incident windows can save the same request more than once.

Search uses the existing read-only dashboard access controls, bounded results and a three-second deadline. Storage work happens only for incidents, in the existing background writer; request ingestion performs bounded in-memory sampling. Retention cleanup runs independently.
